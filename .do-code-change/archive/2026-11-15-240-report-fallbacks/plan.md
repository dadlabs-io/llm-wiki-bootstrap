# Plan — the cycle's report names every fallback from the expected tool path (task #240, lesson #12)

Classification: vertical slice (one user-visible behaviour: the cycle's report has a Fallbacks section that says what left its expected tool path, or says there was none). The first step already gives a user the section on a clean run; later steps add what fills it.

## Problem Statement

A `/wiki-cycle` step can leave its expected tool path (a different agent type, a different fetcher, a retried command, a default model after an unreadable setting file) and the report need not say so; 2026-08-01 a shell timeout was replaced by another tool and the skill's next rule was written around the substitute, not the cause ("the silence is the failure", pre-mortem #12).

## Solution

One general rule in `/wiki-cycle`'s `SKILL.md`: whenever a step used a substitute for its expected path, the orchestrator appends one line to `fallbacks.txt` in the run folder and one line to the scratchpad's Decisions log. Step 0 creates `fallbacks.txt` with a header line. `/wiki-report` reads it and shows a short `## Fallbacks` section just before `## ⚠️ Needs you`: one line per fallback, or the single line `Fallbacks: none`. Its `--brief` mode gains one line, `Fallbacks: N — see the full report`, only when N is above zero. An ingest worker names any fallback in its receipt's Notes column (told by its brief) and the orchestrator copies each into the file. No script, no agent definition and no contract doc changes.

## Implementation Decisions

- **The file is `fallbacks.txt`, plain text, in the run folder.** Not JSON: the suite's common checks require every run-folder `*.json` (bar three named ones) to carry the step fields and an `.md`, and the report is built from step JSONs only (contract invariant 5), which this file is not. Same family as `unfinished-runs.txt`, `promote-setting.txt` and `cost.md`, which the report already reads beside the step JSONs.
- **Exact format** (the orchestrator, a model, writes it; a separator it writes reliably):
  ```
  # fallbacks from the expected tool path: step | expected path | what was used | why
  Step 2 | wiki-ingester workers on the model in wiki-ingester-config.json | the default model, sonnet | the setting file is unreadable (warning from Step 0)
  ```
  Line 1 is the `#` header, written at Step 0, so the file is never empty (a zero-byte file is deleted by Step 9's junk rule and fails the suite's zero-byte check). Each later line has exactly four fields separated by ` | `; a field never holds ` | ` and never holds a `>` character (the `stray-file-alarm` hook reports a stray file from a `>` followed by a word, claude-code #76774). The step field names the step (`Step 2`). The orchestrator appends a line with the file-editing tool, never a shell redirect. A keyword search on a machine set to full (see below) has its `why` begin with the fixed words `departure from the stop-and-report rule:`.
- **One rendering rule for every line of the file, the departure line included.** The report line for a file line `S | E | U | W` is exactly `- S: expected E; used U; why W`, the four fields copied word for word, nothing added, nothing dropped, in file order. There is no second rendering: a departure line is a line whose `W` starts `departure from the stop-and-report rule:`, so it reads `- Step 3: expected a failed search to stop and be reported; used a keyword search; why departure from the stop-and-report rule: the full search exited 75 after retries`. The report adds no `DEPARTURE` label of its own; the fixed words in `W` carry it.
- **Three states for the report**, and only these:
  1. the file holds the header and nothing else → the section's one line `Fallbacks: none`;
  2. the file holds fallback lines → one report line each, by the rendering rule above;
  3. the file is absent (a run begun before this rule, resumed, or `--report-only` on an older run folder) → the one line `Fallbacks: not checked (no fallbacks.txt in the run folder)`, never `none`. One label for every absent-file case, including a rule-era run resumed after its Step 0 with nothing found since (Mark's choice, plan confirmation 2026-11-15). `--resume` does not repeat Step 0, so a resumed run does not create the file; a step of a resumed run that has a fallback to record creates the file with the header first, then appends. Standalone `/wiki-report` (no run folder) omits the section, as it omits the Cost line.
- **`--brief` shows one line, only when there is something to show**: `Fallbacks: N — see the full report`, N the count of fallback lines in `fallbacks.txt`, placed after the Numbers table and before Needs you. With N at zero (state 1), an absent file (state 3) or no run folder, `--brief` shows nothing about fallbacks: the full report's lines are the place for `none` and `not checked`. (Mark's choice, plan confirmation 2026-11-15; the absent-file case reading as nothing in `--brief` is the planner's call, since N is not above zero there.)
- **What counts as a fallback**, stated in the rule so `none` is not ambiguous: a step used a substitute for its expected path: a different agent type (`general-purpose` for `wiki-ingester`), a different fetcher, the transcription after a subtitle 429, a re-run of a script after exit 75, a default where a setting file could not be read, a timeout worked around by another tool; and a keyword search on a machine whose mode is full. The existing specific lines (Step 2's `general-purpose`, `Fallback: transcribed`, the exit-75 re-run, the unreadable setting file) stay as written; the rule adds that each, when it fires, is also recorded. Not a fallback, so never listed: a step that failed with no substitute (already in its step JSON `errors` and the Needs-you lines), a step skipped by mode, a machine set to `search_mode: keyword` searching by keyword, the depth check's `skipped (keyword search)`.
- **The keyword search on a full machine** (requirements Decision 1, decided): the rule names it as a departure from the stop-and-report rule in `/wiki-update` and the 2026-09-13 decision, never as an allowed fallback; that rule's text is not touched. The other half, a machine set to keyword is not listed, has no case (Mark dropped the `keyword-machine` case at plan confirmation, 2026-11-15); it is read from the rule's wording (step 5).
- **The worker's note format has no `>` character**: `Fallback: expected X; used Y; why Z` in the worker's Notes cell, X, Y and Z plain words (the skill text writes the shape with no angle brackets; never `->`). The orchestrator copies each such note into the file as `Step 2 | X | Y | Z`.
- **Where each piece goes in the skill text** (no paths in the steps; the places are named): the general rule is a short paragraph beside "Every step writes `<step>.json` + `<step>.md`"; Step 0 creates the file with its header after the scratchpad; Step 2's worker briefs gain one sentence (a worker names any fallback it used in that item's Notes, in the note format above) and the orchestrator copies each to the file from the receipts; Step 8's list of what the report holds gains the Fallbacks section "just before ⚠️ Needs you"; Step 9's keep list names `fallbacks.txt`, because Step 9 deletes "a file of its own... a name no step or script writes" and this file is written by the orchestrator; `reference.md`'s "Cycle id and run folder" paragraph names it. The scratchpad line goes under the existing Decisions log, `- <now_stamp()> — fallback: <the file's line>` (no template change).
- **`/wiki-report`'s template** gets a `## Fallbacks` section after Numbers and before `## ⚠️ Needs you`, with the three states above; its `--brief` rule gains the one conditional line above; the "Needs you is always the last section" rule and its Don't lines stay.
- **Helpers searched for, none needed**: no new function is written in the skill or scripts (the change is prose, a suite kind and cases). The suite's kind and its prepare/check functions follow `_prepare_unfinished` / `_check_unfinished` (new functions `_prepare_fallbacks`, `_check_fallbacks`, searched for: `fallback` in `check.py`, found none; `_needs_you`, `_scratch_status`, `_agent_calls`, `_prepare_quick`, `_prepare_resume` and `_prepare_models` are reused, not copied).
- **The new kind's preparation** (test code; pins what the cases below need):
  - `fallbacks` is added to the quick-run dispatch tuple in `prompt` (the one reading `("ingest-only", "scratch", "models")`), so `_prepare_quick` queues each id in the case's `queue`; every new case carries a `queue` (`[]` for the clean one). `_prepare_fallbacks` then adds only the variant's own fixture: for `resumed` the existing resume fixture via `_prepare_resume`.
  - `_prepare_models` writes the broken ingester setting file only when the case sets `"ingester_config_broken": true`; the unreadable-config case sets it, the other two do not.
  - Every new case's `env` pins `WIKI_SEARCH_MODE=full` (the runner already passes a case's `env`), so a host set to keyword cannot change a result.
