# Plan: a cycle names everything it leaves undone (task #240, lesson #9)

Revision 7, after the round-7 narrow check (`plan-red-team.md`); it changes only what that report names. Mark's ruling: the plan is complete and solid before building, whole scope, and still splits into two parts. The revision history is in `checkpoints.md`.

Classification: **vertical slice**. Each step adds queues to one section end to end: the script's line, the run-folder file, the report's copy of it, and the test that pins both. Not a wide refactor: nothing is renamed; the existing code touched is a shared "newest completed step" walker and three list-returning extractions in the scope script (step 4). Lowercase "step N" below is a step of this plan; "cycle Step N" is a step of the cycle skill.

## Problem Statement

A `/wiki-cycle` run can end with queues it owns still non-empty (entries past `review_after`, entries with no `review_after`, entries not linted or claimed or synthesised, lint findings, dropped or failed sources, staged entries, discovery checklists, other readers' buckets), and the report names most of them in some modes and none in others. Mark's rule (2026-11-16): after a run, anything left undone is named, with the count and why.

## Solution

One script writes the section; the report copies it. A new `wiki-cycle-scope.py` subcommand, `left-undone --run-folder <rf>`, runs at cycle Step 8 in every mode (`--report-only` included). It counts fresh from the notebook and the run folders' step files and writes `left-undone.txt` in the run folder. **Line 1 of the file is a header the script writes**: `Left undone: nothing`, or `Left undone: <N> queue(s)` (N is the number of queue lines below it, `not checked` lines included, because each is something not known to be empty). A `--report-only` file has a second line, `Disk-state queues are counted now; event lines are from the last run (<id>)` (not counted in N). Then the queue lines, `- <queue>: <N> — <reason and way out>`. **The mode is read, never typed**, from the scratchpad (below). `/wiki-report` pastes the file word for word as a new section "Left undone", just above `⚠️ Needs you` (after Fallbacks). The model computes no count and writes no reason. The section has **three states**, as Fallbacks does: the file's text; `Left undone: not checked (no left-undone.txt in the run folder)` when the run folder has none (a `--resume` of a run begun before the install, a skipped command, a report rebuilt from an old run); and, for a standalone report, `Left undone: not checked (standalone report: no run folder)`. **`--brief` prints line 1 verbatim, followed by ` — see the full report` only when line 1 reads `Left undone: <N> queue(s)`** (not after `Left undone: nothing`, the Part 1 `Left undone (disk-state queues): none`, or the two no-file `not checked` states, which are complete as they stand), after Numbers (the same position as Fallbacks' brief line); it is the file's own line, so no count is composed. Silence is never a state. `⚠️ Needs you` stays the last section.

## Building in two parts

The plan is written whole; each part stands alone.

- **Part 1, the disk-state counts** (steps 1, 2 and 3): what is on disk when the run ends, whatever ran. Past, missing and malformed `review_after`; tickets in `_inbox/pending/`; tickets in this session's buckets and in other readers' and `mark`'s; staged entries; discovery checklists. Part 1 reads no step file's content for a count; the only step-file presence and status it looks at is `refresh.json`'s (to choose the wording of the past-`review_after` reason) and the named step files' presence for the mode cross-check, and it reads the scratchpad for the mode.
- **Part 2, the leftovers of steps that ran** (steps 4, 5 and 6): not-linted, no-claims and not-synthesised entries (they need the step's own scope file and status), lint findings, semantic findings and the fixes record, the earlier-run semantic findings lines (Decisions needed 10), dropped, failed and deferred sources, tier-4 deferrals, and `--report-only`'s copy of the last run's events.
- **One interim form if Part 1 ships alone.** Its file's line 1 is `Left undone: <N> queue(s)`, or `Left undone (disk-state queues): none` when there is none; the queue lines follow; and the file always ends with the line `Not counted yet: leftovers of steps that ran (lint findings, dropped sources, entries not linted, claimed or synthesised)`. `Left undone: nothing` is never written by Part 1. Step 6, the last Part 2 step, removes the last line and the alternative header, and a test asserts both are gone (removing them earlier would let a build between steps 4 and 6 print `Left undone: nothing` while lint findings and sources are still uncounted).
- In a split, each part gets its own `eval-case-writer` brief from that part's requirement (Part 1's clean case reads the interim form). Step 7 runs once per part built (Paid runs, below).

## Implementation Decisions

**The two open questions from requirements, settled.**

1. *Does a new counter change the cycle-step contract?* No. The outputs are plain `.txt` files in the run folder, as `promote-setting.txt`, `fallbacks.txt` and `unfinished-runs.txt` are; the suite reads only `*.json` as steps. No step, no `summary` key, no new JSON field; `framework-docs/` stays unedited (invariant). One drift is noted, not touched: the contract lists the semantic lint's findings as category arrays, while the real file (agentic-design's 2026-10-30 run) holds one flat `findings` list; the counter reads the real shape (below).
2. *Does a failed or skipped ticket stay in its bucket?* Yes. `wiki-dequeue.py` moves a ticket to `done/` only when its `source` URL matches an entry's `source_url`, and keeps every other one. So a failed, deferred or dropped ticket is still in its bucket after the run, and so is one skipped because an entry on the same topic exists under a different URL. Left undone names such a ticket every cycle, with the reason the worker gave and no further way out; not changed here.

**Design rule: derive from files that already exist; a model-run command only where nothing else records the fact.** The script reads the notebook and the run folders' step files; it writes `left-undone.txt` and, in Part 2, `left-undone-events.txt` (the event-class lines, written only by a run that is not `--report-only`), never a `*-scope.txt`, never an entry. One fact has no record on disk: which semantic findings the user applied or declined at cycle Step 5. It is recorded by a script command the model runs (below), by finding **ids that the script itself printed from the JSON**, so the model copies ids and never counts positions. A model step can still be skipped (the scope script's docstring records 21 of 22 runs skipping a sentence), so **the absence of that file reads `not checked`, never a false reason, and never removes the Needs-you line** (below).

**Mode and modifiers.**
- The scratchpad is created at cycle Step 0 in every mode; its template line is `**Cycle**: <cycle_id> (<mode>)` and a second line `- Mode: <mode and flags>` (`reference.md`, the scratchpad template). **The template line changes to `(<mode>[, <modifiers>])`** so the model has a place for `--no-confirm-discovery`, `--lint-all` and the rest on the line the script reads first.
- Tokens are split on whitespace, commas, semicolons and parentheses, with backticks, quotes and trailing punctuation stripped. **The mode is the first token inside the parentheses of the `**Cycle**` line**, one of nine names, each accepted with or without its leading dashes: `quick`, `full`, `ingest-only`, `discover-only`, `prompt-for-urls`, `lint-only`, `report-only`, `refresh-only`, `claims-only` (so `(--full)`, `(full)` and `(lint-only)` all read). Only the first token can name the mode, so the live line `quick (ingest pass; the user asked for "a full ingest"…)` reads as quick. `--semantic` together with `lint-only` (both tokens present in the `**Cycle**` text or the `- Mode:` line) makes it `lint-only-semantic`. **Modifiers** (`--no-confirm-discovery`, `--lint-all`, `--direct`, `--since`) are `--` tokens found anywhere in the `**Cycle**` text or the `- Mode:` line. If the `**Cycle**` line holds no mode token, the `- Mode:` line's first token is tried; if the two lines name different modes, or neither names one, or there is no scratchpad, the mode is unknown.
- **An unknown mode, or one the run folder contradicts, keeps the disk-state counts** and changes only the mode-dependent reasons: each such line reads `<count>, not checked (cannot read the mode from scratchpad.md)` or `<count>, not checked (the mode in scratchpad.md is <mode> but the run folder holds <step>.json)`. Reasons that do not depend on the mode (no `review_after`, malformed dates, other readers' buckets, discovery checklists, staged entries) are printed as usual. The header counts the lines as usual. **The file also carries one queue line, so the header can never read `nothing` while the mode is not known**: `Mode: not checked (cannot read the mode from scratchpad.md); steps that left no file are not known`, or, for a contradiction, `Mode: not checked (the mode in scratchpad.md is <mode> but the run folder holds <step>.json); steps that left no file are not known`.
- Evidence (read-only, all notebooks of the project-notebooks vault): 32 live scratchpads, 16 carry a `**Cycle**:` line (the older ones another layout) and every one starts with the mode as its first token; the 17 `- Mode:` lines listed carry free prose after the mode (`;`, parentheses, quotes). **`--no-confirm-discovery` appears in none of the 32**, in neither line: no live run has recorded it. No reader or eval parses the `**Cycle**` line today (`check.py` and the fixtures only write it), so the parser and its tests are new.
- **Cross-check:** a table in the script says which steps each mode runs (refresh: `full`, `refresh-only`; semantic lint: `full`, `lint-only-semantic`; claims: `full`, `claims-only`; synthesis, triage, ingest: `quick`, `full`, `ingest-only`, with `prompt-for-urls` ingesting and synthesising but not triaging; fix step: `full`; mechanical lint: all modes but `discover-only`, `refresh-only`, `claims-only`, `report-only`; discovery: `quick`, `full`, `discover-only`). A step JSON present in this run folder that the mode's row does not run is a contradiction (above). The check is keyed on the named step files (`refresh.json`, `lint-semantic.json`, `claims.json`, `synthesis.json`, `update.json`, `triage.json`, `discover.json`, `lint-mechanical.json`), never a `*.json` glob: `models.json`, `cost.json` and `email-review.json` are not steps. **Drift test:** the test parses the five-mode markdown table of the cycle skill and asserts the script's table agrees for those five; it does not cover `lint-only`, `report-only`, `refresh-only` and `claims-only`, which the skill states only in prose; for them the cross-check is the only guard, and it catches a step the table says does not run but not one the table says runs that is absent (that reads as the third state).

**The third state, for every step a mode runs.** For each line whose wording depends on a step: **the mode does not run it** → "does not run" wording; **the mode runs it and its JSON is present and `completed`** → the "ran" wording; **the mode runs it and its JSON is absent** → `not checked (<step> left no <file>)`; **present but not `completed`** → `not checked (the <step> ended <status>)`. It applies to refresh (past `review_after`), the semantic lint, claims, synthesis, the mechanical lint, and the fix step (the fixes file: in `full`, absent reads `not checked (the fix step left no lint-fixes.txt)`, and the lint-kind lines keep their counts followed by that text). **It does not apply to ticket counts**: the tickets lines (pending, own bucket) are facts about the folders, true whatever a step's JSON says, and their wording does not read a step file. In every case the count is still printed in the line, before `not checked`.

**What counts.**
- *Entries* are `wiki/` pages minus `_`-prefixed files, `README.md`, and anything `_wiki_config.in_sessions` or `in_tasks` says. Those take a path relative to `wiki/`, so the counter passes `Path(e).relative_to("wiki")`. The script's `entries()` keeps `tasks/` (the semantic lint and refresh skip task cards), so every count filters again.
- *Past `review_after`*: the value parses as a `YYYY-MM-DD` date (quotes stripped, as the shared frontmatter parser does) and is strictly before today (`--today YYYY-MM-DD` for tests, default `today_label()`). *No `review_after`*: the key is absent. *`review_after` not a date*: present and not a calendar date. Three lines; the lint lists them in different places.
- *The Numbers row* (Decisions needed 11, recommended form): the report's Numbers row "Stale (past review_after)" is **the Left undone past line's count when that line exists; 0 when the file exists and has no past line; `not checked` when there is no file** (the report's two not-checked states). `wiki-report` Step 1G's awk counts every page under `wiki/`, task cards and sessions included (on llm-wiki-bootstrap: 186 against 6 once task cards are excluded) and keeps quote characters, so the row today overstates by the cards and misreads quoted dates. The Stale entries table is refresh's own list and is not touched.
- *Staged entries* only when `confirm_before_promote` is `false` (`promote-setting.txt`); with `true` Needs you has them and keeps them.
- *Discovery checklists*: each non-`_`, non-`README` `.md` in `_inbox/discovered/`; discovery files a processed checklist in `_inbox/done/` (`wiki-discover` Step 7, a model step that can be skipped), so one still there has not been filed as processed; whether it was reviewed is not recorded, and the line says only that.
- *Tickets*. Pending: `wiki-triage.py`'s existing `_tickets(nb)` (every `.md` in `_inbox/pending/` not `_`-prefixed or `README`; the dequeue also counts a pending file with no `source:`, so `pending/` has no `source:` rule). Triage moves every ticket out of `pending/`, so one still there in a mode that triages arrived after triage ran (or triage did not complete); that is true whatever triage's JSON says, and only 3 of 32 live run folders hold a `triage.json`, so the line must not read it. Buckets: one new function in `wiki-triage.py`, `intake_tickets(nb)`, yielding `(folder, path, source, front)` for every `.md` in a bucket folder that is not `_`-prefixed, not `README`, not `triage-log.md`, and has a `source:` line (Decisions needed 7). Bucket list and this session's name: `buckets()` and `me()` of `wiki-triage.py`, loaded with `importlib` as `_install_tooling.py` does. `me()` reads the working folder's `.claude/wiki-config.json`, so the command must run from the project whose notebook is counted (the cycle does; the live check in step 7 does too). PyYAML is installed in the scripts environment (6.0.3), so tests run the yaml branch of `_parse_buckets`; its regex fallback (ImportError only) is not exercised. Own-bucket tickets are one line; other readers' and the `mark` bucket are one line for all, `Other readers' buckets, still to process: <folder> N, <folder> N` (Mark, D6): no owner, no reason, no items.
- *Not semantically linted, no claims, not synthesised* (Part 2): **the covered-set rule, one rule for all three, no distinction between "this run" and "an earlier run".**
  - A new function `newest_step(nb, json_name, status=None, skip=None)` returns the newest run folder holding that step's JSON, optionally of one status and skipping one folder. `last_semantic` and `last_synthesis` (the same walk, one ignoring status, one requiring `completed`, both skipping the current folder; exactly two walkers exist) are re-expressed over it; their signatures and outputs stay, and so does every existing test. The counter calls `newest_step` with nothing to skip, so this run's own completed step is the cut-off.
  - Cut-off `C` = the timestamp of the newest *completed* `lint-semantic.json` (claims: the claims index's written time, as `cmd_claims` takes it; synthesis: the newest completed `synthesis.json`). `S` = the `*-scope.txt` in that step's own run folder, the exact list it read. Scope-now is the unchanged scope function at that cut-off, extracted from `cmd_semantic`, `cmd_claims`, `cmd_synthesis` into functions returning the list, so the commands and the counter share one computation (the commands' output and files unchanged).

- *Lint findings* (Part 2): every key of `lint-mechanical.json`'s `summary` above 0 except `files_scanned` (not a finding), `standalone` (it lists pages that declare themselves standalone by design, not findings; the script's docstring says so) and `backlink_blocks_out_of_step` (Needs you has it), one line per kind. **A partial lint** (`status: partial`, the `not_checked` list the lint writes at exit 3) writes one line `Lint: not checked — <reason>` per entry of `not_checked`, whatever the counts say (unchecked parts report 0), and the file is never `nothing`. No lint JSON in a mode that lints is the third state; in a mode that does not lint: `Lint findings: not checked (no lint ran this cycle; /wiki-cycle --lint-only)`.
- *The fixes record and the staleness guard* (Part 2). `lint-fixes --run-folder <rf> --show` prints the findings of `lint-semantic.json` from its `findings` list, one per line, as `<id>. [<category>] <file> — <first 100 characters of detail>`, the id being the finding's 1-based position in that list; **the ids come from this printout, so nobody counts positions** (today's `lint-semantic.md` is a bulleted list under `## high`, `## medium`, `## low` with no numbers, and the merge at cycle Step 4 is written by the model, so the script prints from the authoritative JSON instead of the .md). `lint-fixes --run-folder <rf> --applied <ids> --declined <ids>` writes `lint-fixes.txt` (the two id lists, possibly empty, and an `at:` stamp); an id outside `1..len(findings)`, or in both lists, or non-numeric, is exit 2 and writes nothing; **with no `lint-semantic.json` in the run folder (cycle Step 4 skipped because a lint ran within 24 hours) it writes empty lists and exits 0**. **The file is written at cycle Step 5 whenever the fix step ran, zero ids included, and the guard fires whenever it exists**: when the lint JSON's `timestamp` (tz-aware) is earlier than the file's `at:`, every lint line reads `Lint findings: not checked (the lint predates cycle Step 5; re-run the mechanical lint)`, because mechanical-only fixes leave no id and the lint cannot otherwise know they were made. **Order in cycle Step 5:** show the findings (`--show`), apply what the user approves, run `lint-fixes`, then re-run the mechanical lint (so its stamp is after `at:`), then cycle Step 5.5. (Decisions needed 1 chooses between this and rewording the lines; if reworded, the guard and the re-run are dropped and the lines read "found before the fix step; approved fixes are not subtracted".)
- *Semantic findings* (Part 2): the key is **`findings`**, a list, with `summary.findings` its length (read from agentic-design's 2026-10-30 `lint-semantic.json`: 193 entries, `summary.findings` 193, each `{file, category, severity, detail, evidence, suggested_fix, agent}`; also a top-level `not_checked` list of 2 items and `status: completed`). The count is `len(findings)`; no list, not a list, or a length that disagrees with `summary.findings` gives `Semantic findings: not checked (lint-semantic.json has no usable findings list)`. A non-empty top-level `not_checked` gives one line `Semantic lint, parts not checked: N — <the items>`. A `lint-semantic.json` of status `partial` with a usable findings list prints `Semantic findings: N, not checked (the semantic lint ended partial)` and keeps its Needs-you line; the printed N is the figure the complete line would print (awaiting when a fixes record exists, otherwise `len(findings)`). Awaiting = `len(findings)` minus the distinct ids in `applied` and `declined` of `lint-fixes.txt`, never negative by the validation above. No `lint-fixes.txt` in a mode that runs the fix step is the third state (`Semantic findings: N, not checked (the fix step left no lint-fixes.txt: applied and declined were not recorded)`); in `lint-only-semantic` the count is all findings with `no fix step in this mode`. **The way out is stated truthfully**: no cycle step shows an earlier run's findings again (cycle Step 4's scope is "added or revised since the last semantic lint", and cycle Step 5 shows only this run's findings), so the wording is `the findings are in lint-semantic.md (run <id>); no later cycle step shows them again`, never "a --full run applies them".
- *Semantic findings from earlier runs* (Part 2, Decisions needed 10). The files read are `_inbox/reports/*/*/lint-semantic.json` and the `lint-fixes.txt` beside each, every run folder, this run's own included. In a run with no semantic lint of its own, the **newest completed** `lint-semantic.json` of any run is read, minus that run's `lint-fixes.txt`, and named `Semantic findings from <id>: N — awaiting your approval; the findings are in lint-semantic.md (run <id>); no later cycle step shows them again; fixes made by hand since are not seen` (under the "newest only" answer to Decision 10 the line also reads `only the newest lint is read here, older lints are not`). A run before the install has no `lint-fixes.txt`: `Semantic findings from <id>: N, not checked (that run recorded no applied or declined findings)`. **Said plainly: under the "newest only" form, a newer lint, one with 0 findings or one that covered a single new entry, silences every older lint's unresolved findings, and nothing prints that.** Decisions needed 10 offers the form that never goes silent, recommended: **in every run, whatever it ran (a `--full` or `lint-only-semantic` run included), every completed lint older than the newest one, the newest being this run's own when it ran one, that still has unresolved findings gets its own line**, `Semantic findings from <older id>: N, superseded by a newer lint; not shown again; the findings are in lint-semantic.md (run <older id>); no later cycle step shows them again`, counted from that lint's fixes note and not added to any "awaiting" figure (it also prints when the newest lint has 0 findings). Cost: the script reads each earlier `lint-semantic.json` and `lint-fixes.txt` (3 such files in agentic-design today; each lint file is a flat list, 193 findings in the largest); "not shown again" refers to the report, not to the script. Earlier lints with a **non-empty findings list and no fixes note** collapse into one line, `N earlier lints recorded no applied or declined findings; not shown again`, so they do not add one line each forever; a lint whose findings list is empty prints nothing, and is not counted in that line. These lines count in the header.
- *The reason for a lint kind in `--full`*: the fixers are by category and do not cover every mechanical kind, so "awaiting your approval" would overstate. After the lint re-run, what remains is true by construction and the reason reads `still present after the cycle Step 5 fixes (not approved, declined, or no fix step covers this kind)`. "Awaiting your approval" is used only for semantic findings.
- *Sources* (Part 2): from `update.json`, every `skipped`, `deferred` and `errors` item; from `discover.json`, every `skipped` item except what Decisions needed 5 drops; tier-4 deferrals as below. One line per item, `Source <url or slug>: <skipped|deferred|failed> — <reason as the file holds it>` or `(no reason recorded)`. The listing of tickets already in Needs you is Decisions needed 6. **A step file absent in a mode that runs the step** (`update.json` under `ingest-only`, `discover.json` under `quick`) is `Sources: not checked (<step> left no <file>)`; absent in a mode that does not run it adds no line; a file that exists and cannot be parsed gives `Sources: not checked (<file> unreadable)`.
- *Tier-4 deferrals* (Part 2, Decisions needed 2, recommended form): **only when this run folder holds `discover.json` (this run ran discovery) and `--no-confirm-discovery` is among the modifiers.** A run such as `--ingest-only --no-confirm-discovery` runs no discovery, so an earlier checklist in `_inbox/done/` cannot produce a line. The script finds this run's checklist, `<run date>-discovery.md` (the first ten characters of the cycle id), in `_inbox/discovered/` and, if it is not there, in `_inbox/done/` (a processed checklist is moved there by `wiki-discover` Step 7; whether an unattended run has moved it by cycle Step 8 is not known, so both are read). Two discovery runs on one day share the file name, so the file read is the one that exists; that limit is accepted. A candidate line is `- [ ] **N.** [Title](url) — tier N — **Why**: …`; a line with `tier 4` and an unticked box whose URL `wiki-feeds.py known` reports `new` is a deferred tier-4 source, reason `tier 4: needs your review (--no-confirm-discovery)`. `known` reads only the first 30 lines of each ticket it checks, so a held ticket whose `source:` sits later is reported `new`: a possible extra line, stated, not guarded. No checklist in either folder gives `Tier-4 sources: not checked (no discovery checklist for <date>)`; a checklist with candidate lines and none of tier 4 gives no line. **A miss is silent**: an unattended run that did not write `--no-confirm-discovery` into its scratchpad produces no tier-4 line and no `not checked` (Decisions needed 2).
- *`--report-only` and "last run"* (Part 2): **the last run is the newest earlier run folder that holds a `<id>-run-cycle-report.md` and whose scratchpad mode is not `report-only`**; a report-only run is never chosen and **writes no `left-undone-events.txt`**, so nothing nests. This is the one definition; the cycle skill's "runs 8 from the last run's JSON" points to it. Disk-state queues are counted fresh (the file's second line says so, requirements line 75), and so are the earlier-run semantic lines (they are standing backlogs read from the lint files now, not events of the last run; they are never copied and never written to an events file). The event lines (lint findings, semantic findings, sources, tier-4) are copied from the last run's `left-undone-events.txt`, each ending `(from <id>)`. If the newest such folder has no `left-undone-events.txt` (a run before the install) the section reads `Events of the last run: not checked (that run left no left-undone-events.txt)`; no such folder: `not checked (no earlier run with a report)`. One folder is read for every event line, so "did it run" and "the counts" agree.

Rows about tickets and folders, and the rows with no step named, have no third column.
