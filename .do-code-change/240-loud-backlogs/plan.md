# Plan: a cycle names everything it leaves undone (task #240, lesson #9)

Revision 3, after the round-3 red-team (`plan-red-team.md`). Mark's ruling: the plan is complete and solid before building, whole scope, and still splits into two parts. The revision history is in `checkpoints.md`.

Classification: **vertical slice**. Each step adds queues to one section end to end: the script's line, the run-folder file, the report's copy of it, and the test that pins both. Not a wide refactor: nothing is renamed; the existing code touched is a shared "newest completed step" walker and three list-returning extractions in the scope script (step 3), and one migrated bucket loop in `wiki-triage.py` (step 2).

## Problem Statement

A `/wiki-cycle` run can end with queues it owns still non-empty (entries past `review_after`, entries with no `review_after`, entries not linted or claimed or synthesised, lint findings, dropped or failed sources, staged entries, discovery checklists, other readers' buckets), and the report names most of them in some modes and none in others. Mark's rule (2026-11-16): after a run, anything left undone is named, with the count and why.

## Solution

One script writes the section; the report copies it. A new `wiki-cycle-scope.py` subcommand, `left-undone --run-folder <rf>`, runs at Step 8 in every mode (`--report-only` included). It counts fresh from the notebook and the run folders' step files and writes `left-undone.txt` in the run folder: either `Left undone: nothing` or one finished line per non-empty queue, `- <queue>: <N> — <reason and way out>`. **The mode is read, never typed**: from the `**Cycle**: <id> (<mode text>)` line of that run folder's `scratchpad.md` (Step 0 writes the scratchpad in every mode, and the 12 live scratchpads of agentic-design's 2026-10 runs all carry the line). `/wiki-report` pastes the file word for word as a new section "Left undone", just above `⚠️ Needs you` (after Fallbacks). The model computes no count and writes no reason. The section has **three states**, as Fallbacks does: the file's text; `Left undone: not checked (no left-undone.txt in the run folder)` when the run folder has none (a `--resume` of a run begun before the install, a skipped command, a report rebuilt from an old run); and, for a standalone report, `Left undone: not checked (standalone report: no run folder)`. `--brief` carries the same three states in one line. Silence is never a state. `⚠️ Needs you` stays the last section and keeps every line it has today.

## Building in two parts

The plan is written whole; each part stands alone.

- **Part 1, the disk-state counts** (steps 1 and 2): what is on disk when the run ends, whatever ran. Past, missing and malformed `review_after`; tickets in `_inbox/pending/`; tickets in this session's buckets and in other readers' and `mark`'s; staged entries; discovery checklists. Part 1 reads no step file for a count; the one step file it looks at is the presence of `refresh.json`, only to choose the wording of the past-`review_after` reason, and the scratchpad for the mode.
- **Part 2, the leftovers of steps that ran** (steps 3 to 5): not-linted, no-claims and not-synthesised entries (they need the step's own scope file and status), lint findings, semantic findings, dropped, failed and deferred sources, tier-4 deferrals, and `--report-only`'s copy of the last run's events.
- **One interim form if Part 1 ships alone.** Its file always ends with the line `Not counted yet: leftovers of steps that ran (lint findings, dropped sources, entries not linted, claimed or synthesised)`, and when no queue line is above it the file reads `Left undone (disk-state queues): none` first. `Left undone: nothing` is never written by Part 1. Step 3 removes the line and a test asserts it is gone.
- In a split, each part gets its own `eval-case-writer` brief from that part's requirement (Part 1's clean case reads the interim form). Step 6 runs once per part built (Paid runs, below).

## Implementation Decisions

**The two open questions from requirements, settled.**

1. *Does a new counter change the cycle-step contract?* No. The outputs are plain `.txt` files in the run folder, as `promote-setting.txt`, `fallbacks.txt` and `unfinished-runs.txt` are; the suite reads only `*.json` as steps. No step, no `summary` key, no new JSON field; `framework-docs/` stays unedited (invariant). One drift is noted, not touched: the contract lists the semantic lint's findings as category arrays, while the real file (agentic-design's 2026-10-30 run) holds one flat `findings` list; the counter reads the real shape (below).
2. *Does a failed or skipped ticket stay in its bucket?* Yes. `wiki-dequeue.py` moves a ticket to `done/` only when its `source` URL matches an entry's `source_url`, and keeps every other one. So a failed, deferred or dropped ticket is still in its bucket after the run, and so is one skipped because an entry on the same topic exists under a different URL. Left undone names such a ticket every cycle, with the reason the worker gave and no further way out; not changed here.

**Design rule: derive from files that already exist; a model-run command only where nothing else records the fact.** The script reads the notebook and the run folders' step files; it writes `left-undone.txt` and, in Part 2, `left-undone-events.txt` (the event-class lines, written only by a run that is not `--report-only`), never a `*-scope.txt`, never an entry. One fact has no record on disk: which semantic findings the user applied or declined at Step 5. It is recorded by a script command the model runs, `lint-fixes --run-folder <rf> --applied <ids> --declined <ids>`, where an id is a finding's 1-based position in `lint-semantic.json`'s `findings` list; the script validates every id and writes the file, so the model types ids, never a count. Why this cannot be derived: the fix agents edit entries and the findings list is not updated, so nothing on disk says which finding a given edit answered. A model step can still be skipped (the scope script's docstring records 21 of 22 runs skipping a sentence), so **the absence of that file reads `not checked`, never a false reason**.

**Mode.** The mode text is the parentheses of the scratchpad's `**Cycle**:` line; tokens are split on whitespace and commas; the first token that names a mode (`quick`, `--quick`, `--full`, `--ingest-only`, `--discover-only`, `--prompt-for-urls`, `--lint-only`, `--report-only`, `--refresh-only`, `--claims-only`) is the mode; `--semantic` beside `--lint-only` makes it `lint-only-semantic`; `--no-confirm-discovery` is a modifier read the same way (Decisions needed 2). Live mode texts such as `(--ingest-only, scoped to the 10 repo tickets…)` parse. An unreadable or missing scratchpad, or a mode text with no mode token, makes every mode-dependent reason `not checked (cannot read the mode from scratchpad.md)`; disk-state counts are still written with that reason. **Cross-check:** a table in the script says which steps each mode runs (refresh: `full`, `refresh-only`; semantic lint: `full`, `lint-only-semantic`; claims: `full`, `claims-only`; synthesis, triage, ingest: `quick`, `full`, `ingest-only`, with `prompt-for-urls` ingesting and synthesising but not triaging; fix step: `full`; mechanical lint: all modes but `discover-only`, `refresh-only`, `claims-only`, `report-only`). When this run folder holds a step JSON the mode's row does not run (a completed `refresh.json` under `quick`), the whole file reads `Left undone: not checked (the mode in scratchpad.md is <mode> but the run folder holds <step>.json)`, and the exit code is 0 so the report still builds. **Drift test:** the test parses the five-mode markdown table of the cycle skill (`quick`, `--full`, `--ingest-only`, `--discover-only`, `--prompt-for-urls` against its step rows) and asserts the script's table agrees for those five. It does not cover `--lint-only`, `--report-only`, `--refresh-only` and `--claims-only`, which the skill states only in prose (the paragraph after the table); for them the cross-check is the only guard, and it catches a step the table says does not run but not one it says runs that is absent (that case reads as "step did not complete").

**What counts.**
- *Entries* are `wiki/` pages minus `_`-prefixed files, `README.md`, and anything `_wiki_config.in_sessions` or `in_tasks` says. Those take a path relative to `wiki/`, so the counter passes `Path(e).relative_to("wiki")`. The script's `entries()` keeps `tasks/` (the semantic lint and refresh skip task cards), so every count filters again.
- *Past `review_after`*: the value parses as a `YYYY-MM-DD` date (quotes stripped, as the shared frontmatter parser does) and is strictly before today (`--today YYYY-MM-DD` for tests, default `today_label()`). *No `review_after`*: the key is absent. *`review_after` not a date*: present and not a calendar date. Three lines; the lint lists them in different places. **One past-due number per report.** `wiki-report` Step 1G's awk keeps quote characters, so a `--full` report would otherwise carry two numbers (the Stale entries table and Numbers row, and this line). The Left undone count is the one number: when `left-undone.txt` exists, the Numbers row "Stale (past review_after)" and the heading of the Stale table take their N from the Left undone line, and the table lists refresh's entries as it does today.
- *Staged entries* only when `confirm_before_promote` is `false` (`promote-setting.txt`); with `true` Needs you has them and keeps them.
- *Discovery checklists*: each non-`_`, non-`README` `.md` in `_inbox/discovered/`; discovery moves a processed checklist to `_inbox/done/` (`wiki-discover` Step 7), so one still there is unreviewed.
- *Tickets*: three existing loops are reused or migrated, one new function replaces the look-alikes in the file it lives in, the rest are named and left. Pending tickets: `wiki-triage.py`'s existing `_tickets(nb)` (every `.md` in `_inbox/pending/` not `_`-prefixed or `README`; the dequeue also counts a pending file with no `source:`, so `pending/` has no `source:` rule). Bucket tickets: one new function in `wiki-triage.py`, `intake_tickets(nb)`, yielding `(folder, path, source, front)` for every `.md` in a bucket folder that is not `_`-prefixed, not `README`, not `triage-log.md`, and has a `source:` line (Decisions needed 7). Searched for (`_tickets`, `waiting_tickets`, `cmd_retry_list`, `wiki-list-add.py`'s location scan, `wiki-dequeue.py`'s loop): `cmd_retry_list` loops buckets with the same walk and is **migrated onto `intake_tickets` in step 2**, with its existing retry-list checks as its done line. `_pdf_match.waiting_tickets` (needs an http source and no raw), `wiki-list-add.py`'s URL scan and `wiki-dequeue.py`'s move loop (which also walks `pending/`) have different filters and jobs, and two of them sit outside this change's Scope, so they stay (Out of Scope). Bucket list and this session's name: `buckets()` and `me()` of `wiki-triage.py`, loaded with `importlib` as `_install_tooling.py` does. PyYAML is installed in the scripts environment (6.0.3), so tests run the yaml branch of `_parse_buckets`; its regex fallback (ImportError only) is not exercised. Own-bucket tickets are one line; other readers' and the `mark` bucket are one line for all, `Other readers' buckets, still to process: <folder> N, <folder> N` (Mark, D6): no owner, no reason, no items.
- *Not semantically linted, no claims, not synthesised* (Part 2): **the covered-set rule, one rule for all three, no distinction between "this run" and "an earlier run".**
  - A new function `newest_step(nb, json_name, status=None, skip=None)` returns the newest run folder holding that step's JSON, optionally of one status and skipping one folder. `last_semantic` and `last_synthesis` (the same walk, one ignoring status, one requiring `completed`, both skipping the current folder; exactly two walkers exist) are re-expressed over it; their signatures and outputs stay, and so does every existing test. The counter calls `newest_step` with nothing to skip, so this run's own completed step is the cut-off.
  - Cut-off `C` = the timestamp of the newest *completed* `lint-semantic.json` (claims: the claims index's written time, as `cmd_claims` takes it; synthesis: the newest completed `synthesis.json`). `S` = the `*-scope.txt` in that step's own run folder, the exact list it read. Scope-now is the unchanged scope function at that cut-off, extracted from `cmd_semantic`, `cmd_claims`, `cmd_synthesis` into functions returning the list, so the commands and the counter share one computation (the commands' output and files unchanged).
  - An entry in scope-now is **covered**, so not counted, when its full relative path is in `S`, **or** its stem equals the stem of an `S` line under `_inbox/proposed/` (a staged entry the step read before Step 5.5 promoted it; stems only bridge `proposed/` to `wiki/`, and only when exactly one live entry has that name; a duplicate is not bridged, so it is counted), **and** its `last_reviewed` day is not after `C`'s day. An entry revised after `C`'s day is counted whatever `S` says. An entry the claims step read and found no claims in is in the claims `S`, so it is covered.
  - Subtract only on `status: completed`. In a mode that runs the step, a current-run JSON with another status gives `<queue>: not checked (the <step> ended <status>; what it covered is unknown)`; JSON absent and the semantic lint skipped because one ran within 24 hours (cycle skill Step 4) gives `the semantic lint was skipped: one ran within 24 hours (<id>)`; a completed JSON with no scope file gives `not checked (no semantic-scope.txt in the run folder)`. A `synthesis.json` with status `awaiting_approval` adds no synthesis line (Needs you has it).
  - **Same-day**: a step compares days, so an entry the step read and that was re-reviewed later on `C`'s own day is covered (an under-count); one not in `S` is counted. Whether to accept that is Decisions needed 8; the reason text carries the clause until it is answered.
- *Lint findings* (Part 2): every key of `lint-mechanical.json`'s `summary` above 0 except `files_scanned`, `standalone` and `backlink_blocks_out_of_step` (Needs you has the last), one line per kind. **A partial lint** (`status: partial`, the `not_checked` list the lint writes at exit 3) writes one line `Lint: not checked — <reason>` per entry of `not_checked`, whatever the counts say (unchecked parts report 0), and the file is never `nothing`. No lint JSON in a mode that lints: `Lint findings: not checked (the lint did not complete)`; in a mode that does not lint: `Lint findings: not checked (no lint ran this cycle; /wiki-cycle --lint-only)`. **Staleness guard:** when `lint-fixes.txt` records fixes applied and the lint JSON's `timestamp` is earlier than the file's `at:` line, the line is `Lint findings: not checked (the lint predates the fixes applied at Step 5)`, never a count of already-fixed findings.
- *Semantic findings* (Part 2): the key is **`findings`**, a list, with `summary.findings` its length (read from agentic-design's 2026-10-30 `lint-semantic.json`: 193 entries, `summary.findings` 193, each `{file, category, severity, detail, evidence, suggested_fix, agent}`; also a top-level `not_checked` list of 2 items and `status: completed`). The count is `len(findings)`; no list, not a list, or a length that disagrees with `summary.findings` gives `Semantic findings: not checked (lint-semantic.json has no usable findings list)`. A non-empty top-level `not_checked` gives one line `Semantic lint, parts not checked: N — <the items>`. Awaiting = `len(findings)` minus the distinct ids in `applied` and `declined` of `lint-fixes.txt`; the script rejects an id outside `1..len(findings)` and an id in both lists (exit 2, nothing written), so the result is never negative and the units are findings, not fixes. **No `lint-fixes.txt` after `--full`** (the mode runs the fix step) gives `Semantic findings: not checked (no lint-fixes.txt: the run did not record what was applied)`; in `lint-only-semantic` the count is all findings with the reason `no fix step in this mode`.
- *The reason for a lint kind in `--full`*: Step 5's fixers are by category and do not cover every mechanical kind (`stale_pending`, `task_problems`, `design_behind`, `renamed_terms_left` and others have no stated fixer), so "awaiting your approval" would overstate. With the lint re-run after Step 5 (Decisions needed 1), what remains is true by construction and the reason reads `still present after the Step 5 fixes (not approved, declined, or no fix step covers this kind)`. "Awaiting your approval" is used only for semantic findings.
- *Sources* (Part 2): from `update.json`, every `skipped`, `deferred` and `errors` item; from `discover.json`, every `skipped` item except what Decisions needed 5 drops; tier-4 deferrals as below. One line per item, `Source <url or slug>: <skipped|deferred|failed> — <reason as the file holds it>` or `(no reason recorded)`. The listing of tickets already in Needs you is Decisions needed 6. A step file absent means that step did not run and adds no line; a file that exists and cannot be parsed gives `Sources: not checked (<file> unreadable)`.
- *Tier-4 deferrals* (Part 2, Decisions needed 2, recommended form): only when the scratchpad's mode text carries `--no-confirm-discovery`. The script finds this run's checklist, `<run date>-discovery.md` (the first ten characters of the cycle id), in `_inbox/discovered/` and, if it is not there, in `_inbox/done/` (where `wiki-discover` Step 7 moves a processed checklist; whether an unattended run has moved it by Step 8 is not known, so both are read). A candidate line is `- [ ] **N.** [Title](url) — tier N — **Why**: …`; a line with `tier 4` and an unticked box whose URL `wiki-feeds.py known` (the existing one-call link check from `wiki-discover` Step 4) reports `new` is a deferred tier-4 source, reason `tier 4: needs your review (--no-confirm-discovery)`. No checklist in either folder, or one with no candidate lines, gives `Tier-4 sources: not checked (no discovery checklist for <date>)`; a checklist with candidate lines and none of tier 4 gives no line. Step 8 does not use "not in pending" as the test: Step 1.7 has already moved queued tickets into buckets, which `known` looks through.
- *`--report-only` and "last run"* (Part 2): **the last run is the newest earlier run folder that holds a `<id>-run-cycle-report.md` and whose scratchpad mode is not `report-only`**; a report-only run is never chosen and **writes no `left-undone-events.txt`**, so nothing nests. This is the one definition; the cycle skill's "runs 8 from the last run's JSON" points to it. Disk-state queues are counted fresh. The event lines (lint findings, semantic findings, sources, tier-4) are copied from the last run's `left-undone-events.txt`, each ending `(from <id>)`. If the newest such folder has no `left-undone-events.txt` (a run before the install) the section reads `Events of the last run: not checked (that run left no left-undone-events.txt)`; no such folder: `not checked (no earlier run with a report)`. One folder is read for every event line, so "did it run" and "the counts" agree.
