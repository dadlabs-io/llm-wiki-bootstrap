# Plan: a cycle names everything it leaves undone (task #240, lesson #9)

Revision 2, after the round-2 red-team (`plan-red-team.md`). Mark's ruling: make the plan complete first, whole scope, both halves, buildable later in two parts. The revision history is in `checkpoints.md`.

Classification: **vertical slice**. Each step adds queues to one section end to end: the script's line, the run-folder file, the report's copy of it, and the test that pins both. Not a wide refactor: nothing is renamed or migrated; the only touch to existing code is a shared "newest completed step" walker and three list-returning extractions in the scope script (step 3).

## Problem Statement

A `/wiki-cycle` run can end with queues it owns still non-empty (entries past `review_after`, entries with no `review_after`, entries not linted or claimed or synthesised, lint findings, dropped or failed sources, staged entries, discovery checklists, other readers' buckets), and the report names most of them in some modes and none in others. Mark's rule (2026-11-16): after a run, anything left undone is named, with the count and why.

## Solution

One script writes the section; the report copies it. A new `wiki-cycle-scope.py` subcommand, `left-undone`, runs at Step 8 in every mode (`--report-only` included), given `--mode <the mode name>` (a fixed list; any other value is exit 2). It counts fresh from the notebook and the run folders' step files, and writes `left-undone.txt` in the run folder: either `Left undone: nothing` or one finished line per non-empty queue, `- <queue>: <N> — <reason and way out>`. `/wiki-report` pastes that file word for word as a new section "Left undone", just above `⚠️ Needs you` (after Fallbacks). The model computes no count and writes no reason. The section has **three states**, as Fallbacks does: the file's text; `Left undone: not checked (no left-undone.txt in the run folder)` when the run folder has none (a `--resume` of a run begun before the install, a skipped command, a report rebuilt from an old run); and, for a standalone report, `Left undone: not checked (standalone report: no run folder)`. `--brief` carries the same three states in one line. Silence is never a state. `⚠️ Needs you` stays the last section and keeps every line it has today.

## Building in two parts

Mark may split the build; the plan is written whole and each part stands alone.

- **Part 1, the disk-state counts** (steps 1 and 2): what is on disk when the run ends, whatever ran. Past, missing and malformed `review_after`; tickets in `_inbox/pending/`; tickets in this session's buckets and in other readers' and `mark`'s; staged entries; discovery checklists. Needs no step file.
- **Part 2, the leftovers of steps that ran** (steps 3 to 5): not-linted, no-claims and not-synthesised entries (they need the step's own scope file and its status), lint findings, semantic findings not applied, dropped, failed and deferred sources, and `--report-only`'s copy of the last run's findings.
- **If Part 1 ships alone**, its file must never say a false "nothing": it writes `Left undone: nothing in the queues counted so far (leftovers of steps that ran are not counted yet)`, or its lines followed by the line `Not counted yet: leftovers of steps that ran (lint findings, dropped sources, entries not linted, claimed or synthesised)`. Step 3 removes that wording and a test asserts it is gone. In a split, each part gets its own `eval-case-writer` brief from that part's requirement (Part 1's "nothing" case reads the interim wording).
- Step 6 (cases, docs, finish) runs once per part built; its two cases are the pair for the whole scope, and the split changes only which sessions run (Paid runs, below).

## Implementation Decisions

**The two open questions from requirements, settled.**

1. *Does a new counter change the cycle-step contract?* No. The outputs are plain `.txt` files in the run folder, as `promote-setting.txt`, `fallbacks.txt` and `unfinished-runs.txt` are; the suite reads only `*.json` as steps. No step, no `summary` key, no new JSON field; `framework-docs/` stays unedited (invariant). Where a tier-4 deferral comes from is Decisions needed 2.
2. *Does a failed or skipped ticket stay in its bucket?* Yes. `wiki-dequeue.py` moves a ticket to `done/` only when its `source` URL matches an entry's `source_url`, and keeps every other one. So a failed, deferred or dropped ticket is still in its bucket after the run, and so is one skipped because an entry on the same topic exists under a different URL (the dequeue matches URLs only). Left undone names such a ticket every cycle, with the reason the worker gave and no further way out; not changed here.

**Design rule: derive from files that already exist; a model-written file only where nothing else records the fact.** The script reads the notebook and the run folders' step files; it writes `left-undone.txt` and `left-undone-events.txt` (the event-class lines only, Part 2, for a later `--report-only`) and nothing else, never a `*-scope.txt`, never an entry. Two facts have no record on disk and so need a model-run command: what the user applied and declined at Step 5 (`wiki-cycle-scope.py lint-fixes --run-folder <rf> --applied N --declined N`, a command, so the file is written by the script, not typed by the model), and, only if Decisions needed 2 is answered that way, tier-4 deferrals. A model step can still be skipped (the scope script's docstring records 21 of 22 runs skipping a sentence), so **the absence of each such file reads `not checked`, never a false reason**: after a `--full` run, `lint-semantic.json` present and no `lint-fixes.txt` gives `Semantic findings: not checked (no lint-fixes.txt: the run did not record what was applied)`.

**Modes.** `--mode` is one of `quick`, `full`, `ingest-only`, `discover-only`, `prompt-for-urls`, `lint-only`, `lint-only-semantic`, `report-only`, `refresh-only`, `claims-only`. A table inside the script says which steps each mode runs (the mode table of the cycle skill, one source in code): refresh in `full` and `refresh-only`; semantic lint in `full` and `lint-only-semantic`; claims in `full` and `claims-only`; synthesis, triage and ingest in `quick`, `full`, `ingest-only` (triage also not in `prompt-for-urls`; synthesis and ingest also in `prompt-for-urls`); the fix step in `full`; the mechanical lint in every mode but `discover-only`, `refresh-only`, `claims-only` and `report-only`. The reason wording below takes "this mode does not run X" from the table and "ran" from the step's JSON in the current run folder, so a step in the mode whose JSON is absent or not `completed` never reads as "ran".

**What counts.**
- *Entries* are `wiki/` pages minus `_`-prefixed files, `README.md`, and anything `_wiki_config.in_sessions` or `in_tasks` says. Those take a path relative to `wiki/`, so the counter passes `Path(e).relative_to("wiki")`. The script's `entries()` keeps `tasks/` (the semantic lint and refresh skip task cards), so every count filters again.
- *Past `review_after`*: the value parses as a `YYYY-MM-DD` date (quotes stripped, as the shared frontmatter parser does) and is strictly before today (`--today YYYY-MM-DD` for tests, default `today_label()`). This is `wiki-report` Step 1G's intent; its awk keeps quote characters, so its string compare reads a quoted date as past: a defect of that snippet, not copied and not fixed here. *No `review_after`*: the key is absent. *`review_after` not a date*: present and not a calendar date. Three lines, because the lint lists them in different places.
- *Staged entries* only when `confirm_before_promote` is `false` (`promote-setting.txt`); with `true` Needs you has them and keeps them.
- *Discovery checklists*: each non-`_`, non-`README` `.md` in `_inbox/discovered/`; discovery moves a checklist to `_inbox/done/` once processed (`wiki-discover` Step 7), so one still there is unreviewed.
- *Buckets*: the bucket list and this session's name come from `wiki-triage.py`'s `buckets()` and `me()`, loaded with `importlib` as `_install_tooling.py` does; no second README parser. PyYAML is installed in the scripts environment (6.0.3), so the yaml branch of `_parse_buckets` is what tests run; its regex fallback (ImportError only) is not exercised. A ticket is a `.md` in a bucket folder, not `_`-prefixed, with a `source:` line (the rule `wiki-dequeue.py` uses; Decisions needed 7). It becomes one function in `wiki-triage.py`, `intake_tickets(nb)`, yielding `(folder, path, source, front)`; searched for: `wiki-dequeue.py` has the loop inline and also walks `pending/` and moves files, so it is left alone (Out of Scope). Own-bucket tickets are one line; other readers' and the `mark` bucket are one line for all, `Other readers' buckets, still to process: <folder> N, <folder> N` (Mark, D6): no owner, no reason, no items.
- *Not semantically linted, no claims, not synthesised* (Part 2): **the covered-set rule, one rule for all three, no distinction between "this run" and "an earlier run".**
  - A new function `newest_step(nb, json_name, status=None, skip=None)` returns the newest run folder holding that step's JSON, optionally of a given status and skipping one folder. `last_semantic` and `last_synthesis` (the same walk, one ignoring status, one requiring `completed`, both skipping the current folder) are re-expressed over it, so the repository holds one walker; their signatures, outputs and every existing test stay as they are (invariant). No other signature changes; the counter calls `newest_step` with no folder to skip, so the current run's own completed step is the cut-off.
  - Cut-off `C` = the timestamp of the newest *completed* `lint-semantic.json` (claims: the index's written time, as `cmd_claims` takes it; synthesis: the newest completed `synthesis.json`). `S` = the `*-scope.txt` in that step's own run folder, the exact list it read. Scope-now is the unchanged scope function with that cut-off (extracted from `cmd_semantic`, `cmd_claims`, `cmd_synthesis` into functions returning the list, so the commands and the counter share one computation; the commands' output and files are unchanged).
  - An entry in scope-now is **covered**, so not counted, when its full relative path is in `S`, **or** its stem equals the stem of an `S` line under `_inbox/proposed/` (a staged entry the step read before Step 5.5 promoted it; stems only bridge `proposed/` to `wiki/`, and only when exactly one live entry has that name; a duplicate name is not bridged, so it is counted), **and** its `last_reviewed` day is not after `C`'s day. An entry whose `last_reviewed` is later than `C`'s day is revised since, so it is counted whatever `S` says. An entry the step read and found no claims in is in the claims `S`, so it is covered: "no claims" never repeats for an entry the claims step already read.
  - Subtract only on `status: completed`. In a mode that runs the step, a current-run JSON with another status gives `<queue>: not checked (the <step> ended <status>; what it covered is unknown)`; with the JSON absent and the semantic lint skipped because one ran within 24 hours (`SKILL.md` Step 4), the reason is `the semantic lint was skipped: one ran within 24 hours (<id>)`; a completed JSON with no scope file gives `not checked (no semantic-scope.txt in the run folder)`. A `synthesis.json` with status `awaiting_approval` adds no synthesis line (Needs you has it).
  - Same-day: `revised_since` compares days, as the step does. After the rule, an entry re-reviewed on `C`'s own day and read by that step is covered; one re-reviewed that day and not in `S` is counted (the step would read it next).
- *Lint findings* (Part 2): every key of `lint-mechanical.json`'s `summary` above 0 except `files_scanned`, `standalone` and `backlink_blocks_out_of_step` (Needs you has the last). No lint JSON in a mode that lints gives `Lint findings: not checked (the lint did not complete)`; in a mode that does not lint, `Lint findings: not checked (no lint ran this cycle; /wiki-cycle --lint-only)`. **Staleness guard:** when `lint-fixes.txt` shows `applied` above 0 and the lint JSON's `timestamp` is earlier than that file's `at:` line, the lint predates the fixes, so the line is `Lint findings: not checked (the lint predates the fixes applied at Step 5; Decisions needed 1)`, never a count of already-fixed findings as awaiting.
- *Semantic findings not applied* (Part 2): findings in `lint-semantic.json` (sum of its category arrays) minus `applied` and `declined` from `lint-fixes.txt`; one count, "awaiting your approval". Counting a declined finding as awaiting would state something false, so the file records both numbers (a plan decision, not a choice for Mark).
- *Sources* (Part 2): from `update.json`, every `skipped`, `deferred` and `errors` item; from `discover.json`, every `skipped` item except those Decisions needed 5 drops; tier-4 deferrals from the source Decisions needed 2 names. One line per item, `Source <url or slug>: <skipped|deferred|failed> — <reason as the file holds it>` or `(no reason recorded)`. The listing of tickets already in Needs you is Decisions needed 6. A step file absent means that step did not run and adds no line (the tickets lines' reasons already say the mode does not ingest); a file that exists and cannot be parsed gives `Sources: not checked (<file> unreadable)`.
- *`--report-only` (Part 2)*: **"last run" is the newest earlier run folder that holds a `<id>-run-cycle-report.md`** (the inverse of the unfinished-runs test); the script finds it itself. Disk-state queues are counted fresh. The event-class lines (lint findings, semantic findings, sources) are copied from that folder's `left-undone-events.txt`, each ending `(from <id>)`. No such folder, or one with no `left-undone-events.txt` (a run before the install), gives `Events of the last run: not checked (<why>)`. One folder is read for every event line, so "did it run" and "the counts" always agree.

**The line wording, one table** ("this mode does not run X" comes from the mode table, "ran" from the step's completed JSON):

| Queue | Mode does not run it | Ran |
|---|---|---|

## Decisions needed

Seven; each stands alone. Folded away by the design above, so not asked: the `_inbox/discovered/` line (included: discovery files a processed checklist away, so one still there is unreviewed), day granularity (settled by the scope-file subtraction; evidence: 94 of 209), claim-less entries (settled by the claims scope file; at most 2 of 123), the shape of the fixes record (applied and declined, because counting a declined fix as awaiting is false).

1. **How should a lint finding that you fixed at Step 5 stop showing as "awaiting your approval"?**
   Plain background: in a `--full` run where nothing is promoted automatically (the setting is `true`), the mechanical lint runs once, before Step 5. If you approve fixes at Step 5, the lint's saved result still lists the old findings. The report would then say findings are waiting for your approval after you already approved them.
   Recommendation: after the fixes are applied at Step 5, the cycle runs the mechanical lint once more (the same command Step 3 runs; seconds), so its result describes the fixed notebook. As a guard, if fixes were applied and the lint result is older than that note, the line reads "not checked (the lint predates the fixes)" instead of a count.
   Alternative: do not re-run the lint; word the line "found by the lint before the fix step; approved fixes are not subtracted". Risk: the line names findings you already fixed, until the next cycle's lint.
   [ ] re-run the lint after Step 5  [ ] reword the line

2. **Where do the tier-4 sources deferred in an unattended run come from?**
   Plain background: when a cycle runs without you present (`--no-confirm-discovery`), it queues discovery's tier 1-3 sources and defers tier 4. Today nothing records that deferral. Discovery only labels such candidates "(NEEDS HUMAN REVIEW)" in its checklist, and no script, skill or test reads `discover.json`'s `deferred` list (the contract defines it as items to retry).
   Recommendation: read them from the checklist discovery already writes: every candidate line labelled "(NEEDS HUMAN REVIEW)" that is not in the pending queue is a deferred tier-4 source, named with its reason "tier 4: needs your review". The cycle passes `--unattended` to the command when the run had `--no-confirm-discovery`; no new model-written file and no contract change. If the checklist is missing or unreadable the line reads "not checked".
