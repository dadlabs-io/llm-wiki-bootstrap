## 2026-09-14

### `project/code-changes/` — one summary per finished code change, working files in `raw/` (user, with agent-builder)
- **What**: the do-code-change pack's finish step (agent-builder) files each finished change into the project wiki. Agreed in #agent-chat and ruled by the user: the summary is an ordinary entry, `wiki/project/code-changes/<date>-<change>.md` (tags: `code-change` + a group + specific tags; `tier: self`; a `## TL;DR`; Related links to the folder README, the previous change and the decisions/components it touched); the run's working files (requirements.md, plan.md, review-findings.md, *.json) are copied unchanged into `raw/code-changes/<date>-<change>/`, which the summary's `raw_path` names; the folder's `README.md` holds the per-project tag table (Group | Tag | What it means | Don't call it) under a first paragraph the MAP uses as the folder description.
- **Why raw/**: every script that walks `wiki/` would otherwise need an exception for the working files — the lint's six frontmatter checks, both indexes, the MAP, search, and the backlinks script, which writes a backlinks block into every `.md` under `wiki/` and so would edit `plan.md`. Under `raw/` none of them look; search stays lean (qmd indexes `wiki/` only). The cost, accepted: text only in a plan or review is not searchable — the summary carries the decisions, and the full files are also in the code repo's history.
- **Framework change**: `project/code-changes` joins `MERGED_TAXONOMY` (recognised by the folder guards and `wiki-promote.py`, not scaffolded — created on first filing); the frontmatter spec's `raw_path` table gains the folder case and names the one exception to "omit `raw_path` for tier `self`" — a self-authored entry summarising artifacts preserved under `raw/` (`framework-version` 6 → 7); the lint's `raw_path` wording says "file or folder" (its check already accepted a folder). The summary is filed with `wiki-update.py --tier self --folder project/code-changes --raw-path raw/code-changes/<date>-<change>/` (a local source plus `--raw-path` copies nothing); the filename is the slug of the title, so a title starting `<date> <change>` gives a date-first file. With `tier: self`, fewer than two Related links is a warning, not a refusal; the TL;DR is required.
- **Migration**: `install-wiki.ps1 -RefreshOnly`; SOP docs refresh for the spec.

### Entry layout enforced (body → footer → backlinks block); retired entries leave the INDEX, MAP and search; dedup catches case and staged copies (user: "stick with the patterns")
- **What was wrong**: `wiki-update.py` writes an entry as its body (TL;DR … `## Related in this wiki`), then the Source/Raw footer, and `wiki-reciprocate-backlinks.py` appends its block after that. ## 2026-09-13

### Ingest workers use the full search — `wiki-qmd-query.py`, two GPU slots, no keyword fallback (user decision)
- **What changed and why**: since 2026-09-12, parallel ingest workers searched with `qmd search` (keyword only) because four workers each running `qmd query` had locked the machine. The user asked whether the lock-up was really the missing CUDA runtime; a test with CUDA installed (8 GB RTX 4070 Laptop GPU) showed two concurrent `qmd query` run normally and a third fails fast with "Failed to create any rerank context" (GPU memory peaked 6,841 of 8,188 MiB) — no hang. So the lock-up was the Vulkan hang, multiplied. The user's decision: quality over speed — every search is the full search, and when the GPU is full the answer is waiting or fewer workers, never a keyword downgrade.
- **New script `wiki-qmd-query.py`** (in `TRAVEL_SCRIPTS`): runs `qmd query` holding one of two GPU slots (OS file locks released when the process ends, so a crash never leaks a slot; a third caller waits); a 120-second timeout that kills the whole process tree; on a GPU-full error it backs off and retries, then exits 75 — never a keyword fallback; `--preflight` is the `/wiki-search` CUDA check; every call is logged with its wait and run time and `--stats` summarises them, so "is it slower?" is answered from data. It starts qmd as `node <pkg>/dist/cli/qmd.js`, because npm's Windows shim hands off to `/bin/sh` and fails outside Git Bash.
- **Skills and agent**: `/wiki-update` step 3, `/wiki-search` (preflight note, modes table, examples), `/wiki-discover` dedup search and the `wiki-ingester` agent (step 3: preflight once, full search through the helper, a search that still fails marks the item "failed: full search unavailable" rather than filing it without cross-links) all go through the helper; `/wiki-cycle` keeps 4 workers, puts `--stats` in the cycle report and says to run 3 or 2 workers if waiting makes batches slow. Reading list and the wiki-search pack page updated.
- **Scope and depth (same night, user)**: a bare `qmd query` searches every indexed notebook, so an ingest worker filing into one notebook could pick a cross-link from another. `--notebook <name>` (resolved through the registry to qmd's collection, which is named by the folder it indexes; a notebook without a collection is a stop with the `qmd collection add` fix) is now passed by `/wiki-update`, `/wiki-discover` and the `wiki-ingester` agent; `--all-notebooks` is the explicit everything search; a lookup with neither stays unscoped until the user decides the default. The helper's depth is named for what it is: `-k`, results returned after reranking (default 10; qmd's own flag is `-n`, default 5), and `-C`, candidates the reranker scores (default 40; an entry outside the top C never reaches the reranker) — both flags, both settable machine-wide as `$WIKI_QMD_K` / `$WIKI_QMD_C`, both logged per search.
- **Depth tied to wiki size (same night, user)**: a depth test on agentic-design (1,211 files, 8 queries, k=40) found 35 entries C=100 ranked in its top 20 that C=40 never returned — the wiki's canonical memory-architecture page at #7, "10 RAG Patterns" at #4, HIL-Bench at #3 — while C=100 cost about 2 s more per search (median 15.9 s vs 13.6 s). So `-C` now defaults to 8% of the searched collection's files, rounded up to 10, within 40–200 (agentic-design 100, the small notebooks 40, all notebooks together 170), and `-k` to 20 for everyone (the flat score plateau from #3 to #15 means rank order there says little, so show more and let the reading model judge). Searches default to the current project's notebook; `--all-notebooks` on request. `_MAP`/`_INDEX` are dropped from results (they ranked as candidates). `--depth-check` samples entry titles, searches each at C and 2C, and reports what 2C finds that C misses, logged to `depth-checks.jsonl`; `/wiki-cycle --full` runs it so a notebook that outgrows the 8% rule is noticed. `maggies-computer-notes` added to qmd (it had no collection, so nothing could search it).
- **Migration**: `install-wiki.ps1 -RefreshOnly` (new script, three skills, the agent and its reading list); SOP refresh of the wiki-search pack page.

## 2026-09-12

### `qmd query` hang root-caused: Vulkan fallback without a CUDA runtime; CUDA preflight added; truth-status filter fixed
- **Root cause, measured**: `qmd query` runs three bundled GGUF models in-process through node-llama-cpp (Ollama is not involved). With no CUDA runtime installed it fell back to Vulkan across an RTX 4070 + Intel iGPU, where token generation never returned (model loads in 2 s, a 60-token generation ran past 118 s), so every never-seen query hung at the expansion step at 100% CPU on all 32 cores; repeat queries only looked fine because expansions are cached. Four parallel ingest workers each running it locked the machine (11 stalled processes killed). CPU-only (`QMD_LLAMA_GPU=false`) generated but node-llama-cpp reported zero math cores and reranking six chunks exceeded 120 s.
- **Fix**: the CUDA 13.2 runtime — `winget install --id Nvidia.CUDA --version 13.2 --exact --override "-s cudart_13.2 cublas_13.2"` (runtime + cuBLAS only; 13.1+ toolkits no longer bundle a driver; node-llama-cpp's prebuilt CUDA binary needs 13.1+). After it: `gpu=cuda`, 24 math cores, the hung generation takes 0.8 s, a fresh full `qmd query` runs in 16 s. Shells opened before the install lack the CUDA PATH until restarted.
- **Policy (user decision)**: local search stays the default; there is no cloud fallback. `/wiki-search` gains a **CUDA preflight** (`node-llama-cpp inspect gpu` must print `CUDA: available`) and runs `qmd query` under `timeout 120`; a failed preflight or a timeout is reported and fixed, never worked around. Parallel ingest workers use `qmd search` (keyword, no model) — one GPU cannot host several model-loading processes; `qmd query` is for the interactive session. `/wiki-update` step 3, `/wiki-discover`, the `wiki-ingester` agent and its reading list say the same.
- **`wiki-search-rerank.py` fixed** to accept qmd 2.1's bare-list JSON and its `qmd://` file URIs — before this every row was dropped as "does not exist on disk" (or the script crashed on a list).
- **Migration**: `install-wiki.ps1 -RefreshOnly`; install the CUDA runtime on any machine where the preflight fails.
